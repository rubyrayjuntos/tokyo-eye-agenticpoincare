========================================================================
1. Executive summary
========================================================================
The current system violates the intended source-of-truth chain in three places:

1. Backend route mismatch
   - /api/structures/{id}/hydrate tries to build a single curated snapshot,
     but its embedding-run resolver picks the newest embedding run regardless
     of space type.
   - For 4uj1, that means it selects the newest EUCLIDEAN run id, then later
     filters for HYPERBOLIC rows, producing zero embedding residues.

2. Raw embeddings endpoint bypasses curation
   - /api/structures/{id}/embeddings reads directly from fact_gnn_node_embedding
     and returns all hyperbolic rows for the structure without pinning to a single
     latest hyperbolic run.
   - For 4uj1, it returns 714 residues because it is merging two hyperbolic runs
     (357 + 357), not one authoritative run.

3. Science/data inconsistency
   - The science model code says hyp_projections are valid native Poincare disc
     coordinates clamped to radius <= 0.99.
   - The database currently stores hyperbolic 2D coordinates for 4uj1 at ~1e-40,
     i.e. effectively zero.
   - That means either:
       a) the science engine produced collapsed coordinates,
       b) serialization/writeback altered them,
       c) the wrong representation is being persisted or read.

The temporary frontend backfill addresses only the symptom that hydrate returned
0 residues while the direct embeddings endpoint returned >0. It does not resolve
the deeper governance issue.

4. What the backend server is doing
========================================================================
4.1 Direct embeddings endpoint is not governed enough

File:
- agent/coordinator/routers/dashboard.py:369-432

Behavior:
- Queries fact_gnn_node_embedding joined to embedding_space
- Filters only on:
  - structure_id
  - space_type = 'hyperbolic'
- Does NOT constrain to a single run_id
- Orders only by residue_index

Result:
- It merges all hyperbolic runs for the structure.
- For 4uj1, that means 714 rows instead of 357.

Governance implication:
- This endpoint is not returning one authoritative current state.
- It is returning a historical union of hyperbolic rows.

4.2 Hydrate route is attempting curation, but resolves the wrong embedding run

Files:
- agent/coordinator/routers/dashboard.py:672-871
- agent/coordinator/routers/dashboard.py:957-1136
- agent/coordinator/routers/dashboard.py:1097-1136

Route behavior:
- hydrate_structure() calls _fetch_structure_analysis_snapshot()
- snapshot builder calls _resolve_latest_productive_run_metadata()
- then _fetch_embeddings_for_hydration(structure_id, run_id=<resolved embeddings run>)

Resolver behavior:
- _resolve_latest_productive_run_metadata() uses fact_gnn_node_embedding joined to provenance_run
- It picks the latest run by run_ts DESC, computed_at DESC
- It does NOT distinguish euclidean vs hyperbolic for the "embeddings" surface

For 4uj1, the DB ordering is:
- dtie_d8c34c16f0de_euc   (newest)
- dtie_d8c34c16f0de_hyp   (slightly older)

So hydrate resolves:
- embeddings run id = dtie_d8c34c16f0de_euc

Then _fetch_embeddings_for_hydration() does:
- WHERE e.structure_id = :structure_id
- AND es.space_type = 'hyperbolic'
- AND e.run_id = :run_id

For 4uj1 + run_id dtie_d8c34c16f0de_euc:
- hyperbolic row count = 0

This is the concrete reason hydrate reports:
- structure_snapshot.residues = []
- embeddings = null
- context_summary.residue_count = 0

But it still reports:
- latest_run_ids_by_pipeline.embeddings = dtie_d8c34c16f0de_euc

Governance implication:
- The curated snapshot path is selecting a non-authoritative run for the consumer it serves.
- This is a backend read-model bug, not a frontend-only problem.

6. Database vs science comparison
========================================================================
Expected from science contract:
- Hyperbolic run should provide a meaningful native disc projection per residue.
- Euclidean and hyperbolic runs are distinct products and must not be conflated.

Observed in DB:
- Distinct euclidean and hyperbolic runs do exist.
- Hyperbolic rows for 4uj1 exist.
- Hyperbolic 2D coordinates are numerically collapsed near zero.
- The backend "latest embeddings" resolver chooses the newer euclidean run when asked
  for the latest embedding surface.

Conclusion:
- The DB does contain the source facts, but the facts are not yet cleanly governed
  into a single trustworthy read model.
- There are TWO issues:
  1. consumer selection bug (backend choosing the wrong run / merging runs)
  2. science/data quality bug (hyperbolic coordinates look invalid)

========================================================================
7. Why the current cockpit is not trustworthy yet
========================================================================
The cockpit currently allows all of these contradictory states at once:

- Structure list says has_embeddings = true
- Hydrate snapshot says residue_count = 0
- Direct embeddings endpoint says residue_count = 714
- DB latest hyperbolic run actually has 357 rows
- DB hyperbolic coordinates are effectively all zero
- Science contract says those coords should be valid disc positions

This is exactly the kind of multi-truth system that breaks auditability.

========================================================================
8. Governance controls needed
========================================================================
1. Define a single authoritative embedding product for each consumer
   - "latest hyperbolic embedding run"
   - "latest euclidean embedding run"
   - "latest current residue state"
   Do not use a generic "latest embeddings" concept when the DB stores multiple spaces.

2. Backend read models must query governed views or explicit selectors
   - hydrate should use a latest-hyperbolic selector for disc-facing residue state
   - direct /embeddings should pin to one run, not merge historical runs

3. Snapshot invariants must be enforced
   Examples:
   - if latest_run_ids_by_pipeline.embeddings exists, then residue_count must be > 0
   - if has_embeddings = true in structure list, then a current embedding run must resolve cleanly
   - if a curated snapshot returns graph/sites/leaks but no embeddings, return degraded status explicitly

4. Science-to-DB validation must be added
   Before or during write:
   - validate hyp_projections radius distribution
   - reject or quarantine near-zero/collapsed coordinates
   - persist diagnostic metadata so a bad run is visibly bad, not silently accepted

5. State machine should ingest one validated read model
   - not panel-specific endpoints
   - not mixed direct + snapshot data
   - not frontend-local arbitration

========================================================================
9. Immediate root causes
========================================================================
Root cause A: hydrate selects euclidean run id for embedding surface
- This is why the curated snapshot drops residues to zero.

Root cause B: /embeddings endpoint merges multiple hyperbolic runs
- This is why the direct path shows 714 residues instead of one canonical 357-row run.

Root cause C: persisted hyperbolic coordinates for 4uj1 are effectively zero
- This is why even when data exists, the disc view is not scientifically believable.

========================================================================
10. Recommended next decisions
========================================================================
If the architecture is:
DB -> state-machine-centered server read model -> cockpit/agent

then the next concrete decisions should be:

1. Choose the canonical DB read model for "current structure state"
   - likely a governed view or structured snapshot query that explicitly prefers latest hyperbolic residue state

2. Remove raw fact-table reads from UI-serving routes where they bypass curation

3. Make the snapshot contract explicit about degraded states
   - no silent 0 residue counts when an embeddings run exists

4. Investigate the science output for dtie_d8c34c16f0de_hyp
   - are the ~1e-40 coords already present before normalizer write?
   - if yes, the issue is upstream in inference/projection generation
   - if no, the issue is in adapter/write serialization

========================================================================
11. Bottom line
========================================================================
The frontend audit was correct, but incomplete by itself.

Cross-layer comparison shows:
- the frontend contradiction is caused by a real backend read-model bug,
- that bug is exposed because the DB stores separate euclidean and hyperbolic products,
- and even the correct hyperbolic product currently appears numerically untrustworthy.

So the larger issue is not "frontend state drift" alone.
It is a full governance gap across:
- run selection,
- read-model construction,
- and validation of scientific outputs before they become trusted database facts.
